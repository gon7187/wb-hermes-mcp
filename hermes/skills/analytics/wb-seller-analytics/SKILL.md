# WB Seller Analytics

Используй только сервер `wb`. Не запрашивай у пользователя токен и не делай
прямые HTTP-вызовы.

## Основные источники

- карточки: `wb_list_cards`;
- дамп всех названий каталога: `scripts/wb_dump_titles.py` →
  `/root/.hermes/data/wb_all_titles.json` (nmID, vendorCode, title,
  subject, brand, dimensions — для аудита кодов 1С в названиях,
  цвета в названиях, отсутствующих размеров);
- **Питфолл textSearch (03.08.2026):** `wb_list_cards` с
  `filter.textSearch` по vendorCode (например «П00304675») возвращает
  **0 результатов** — textSearch ищет по названию/баркоду, но не по
  артикулу продавца. Поиск по числовому nmID работает. Workaround для
  поиска по vendorCode: полный перебор курсором (`wb_dump_titles.py`
  или пагинация `wb_list_cards` с `filter.withPhoto: -1`) и фильтрация
  локально по множеству target `vendorCode`/`nmID`;
- текущие остатки WB: `wb_get_wb_warehouse_stocks`;
- товарный отчёт остатков: `wb_get_stock_products`;
- продажи: `wb_list_sales`;
- кампании: `wb_list_campaigns`, `wb_get_campaign_budget`;
- реклама: `wb_get_campaign_stats`, `wb_get_campaign_spend_history`;
- **воронка конкретной РК:** `wb_get_campaign_stats` — источник истины для показов (`views`), кликов, CTR, добавлений в корзину (`atbs`), CR, заказов, расхода (`sum`), выручки (`sum_price`) и CPC; запросы идут по `campaign_ids` до 50 за вызов, разрезы лежат в `days → apps → nms`;
- `wb_get_search_queries` не использовать вместо рекламной статистики РК: это товарная поисковая аналитика, а не рекламный разбор кампании;
- локальные сводки:
  `/root/.hermes/scripts/wb_adv_today_live.py`,
  `/root/.hermes/scripts/wb_budget_dashboard.py`,
  `/root/.hermes/scripts/wb_camp_health.py`.

## Рекламный бюджет: правило Максима (01.08.2026)

- Недельный бюджет = **5% от GMV прошлой недели (пн–вс)**. Дневной = `weekly / 7`. GMV для этого расчёта — `priceWithDisc` продаж минус возвраты; R-строки могут уже быть отрицательными, вычитай `abs(amount)` ровно один раз.
- Крон пересчёта запускает без аргументов `wb_weekly_budget_update.py`: только MCP-продажи, атомарная запись и read-back бюджета. Дашборд отдельно читает свежий бюджет и не пересчитывает его. Сбой длинного рекламного сбора не должен блокировать публикацию бюджета.
- Планируй понедельничный пересчёт ДО утреннего дашборда: бюджет `7f600e5714c0` — 08:00 MSK понедельник (`0 8 * * 1`), дашборд `c33b3feb1b51` — 08:30 ежедневно. Иначе проверка текущей недели закономерно падает каждый понедельник. Меняй расписания через `hermes cron edit`, предварительно сохрани backup и затем сравни read-back, включая неизменность остальных заданий.
- Для no-agent дашборда проверяй фактический `cron.script_timeout_seconds` и приоритетный `HERMES_CRON_SCRIPT_TIMEOUT` процесса gateway, а не `terminal.timeout` или агентский inactivity timeout. Восемь рекламных батчей с семью паузами по 65 секунд требуют минимум 455 секунд только ожидания плюс API/ретраи. Наличие продаж за все семь дней не доказывает окончательную финализацию источника WB; при отсутствии/невалидности данных оставляй ошибку, не выдавай старую неделю за новую.
- Актуальные значения — только в `/root/.hermes/data/wb_ad_budget.json` (`daily_budget_rub`, `weekly_budget_rub`). Файл обновляет крон `7f600e5714c0` каждый понедельник.
- Ежедневный контроль (`c57ee9e2f113`) и любые отчёты **читают этот файл** и подставляют реальные цифры. **Никаких хардкодов** фиксированных сумм в промптах, отчётах и памяти.
- Если файл отсутствует или пуст — не придумывать цифры, сообщить об ошибке.
- Источник истины по фактическому расходу — `wb_get_campaign_spend_history` (см. раздел ниже).
- **Питфолл (01.08.2026): хардкод в cron-промптах протухает молча.** Промпт ежедневного контроля содержал «250к₽/день, 1.75 млн₽/неделю» прямо в тексте — после пересчёта бюджета отчёты неделю шли со старой цифрой, пока Максим не спалил. Правило: числа бюджета живут ТОЛЬКО в `wb_ad_budget.json`; в промптах кронов — инструкция «читай файл», без примеров цифр даже в негативной форме. При изменении правил бюджета — grep по `/root/.hermes/cron/jobs.json` на старые суммы, а не только правка основного крона.
- Расчётный крон `7f600e5714c0` считает GMV за ПОЛНУЮ прошлую неделю **пн–вс (7 дней)** — ранняя версия брала пн–пт (5 дней), Максим это отверг.

Для расхода на рекламу всегда добавляй сегодняшний live-результат
`wb_adv_today_live.py`.

- Live-скрипт включает пригодные завершённые РК (7) вместе с 4/9/11 и фильтрует реально удалённые/без товаров. Не добавляй завершённые повторно. `collection_complete` означает успех всех запрошенных батчей, НЕ полноту строк или кабинета: проверяй `row_coverage_complete`, `missing_campaign_ids`, `excluded_campaign_ids`, `account_completeness`. Отсутствующие строки не являются доказанным нулём. Полный перебор сотен РК занимает 8+ минут; не ставь короткий таймаут.
- Текущий день в `wb_get_campaign_spend_history` может быть неполным из-за
  задержки биллинга. Не заменяй более свежий live-расход меньшим биллинговым
  числом без проверки полноты.
- Сверяй `updated_at` и неделю в файле бюджета с текущей датой. Успешный
  запуск крона не доказывает обновление файла. Протухший бюджет обозначай как
  последний сохранённый; не выдавай его за пересчёт текущей недели.
- «Вчерашний расход + пополнение новых РК» — сценарий при полном расходовании
  пополнений, а не прогноз или дневной лимит. При завершении РК учитывай их
  фактический сегодняшний расход отдельно от убранного вчерашнего ориентира. Если API вернул ошибку или неполные данные, явно
пометь результат как частичный; не подгоняй цифры.

## Темп и лимиты (проверено 2026-07-24)

- `wb_adv_today_live.py` работает ~4–5 минут: кампании со статусами
  [4, 9, 11] (~150 шт) бьются на пачки по 50, между пачками sleep 65с
  из-за rate limit. Запускать в фоне (`background=true` +
  `notify_on_complete`) или с timeout ≥ 300с. Таймаут 120с убивает его
  на середине — это не зависон, просто долго.
- Rate limit WB реальный и может быть агрессивнее, чем «65с между
  запросами»: параллельные вызовы `wb_get_campaign_stats` отклоняются
  (`rate_limited`, retryable), но даже строго последовательно с паузами
  65→90→120с три ретрая подряд могут отклоняться. Окно блокировки иногда
  длится минуты. Если 2 ретрая с паузой ≥65с оба вернули `rate_limited`
  — **не крутить дальше**, см. «Fallback на кэш» ниже.
- **Fallback на кэш для прошлых дней:** когда `wb_get_campaign_stats`
  упирается в rate limit, для любых дат кроме сегодня используй SQLite
  `/root/.hermes/data/wb_adv_stats.db` (см. скилл `wb-adv-stats-cache`).
  Данные в нём верифицированы: сверка 32 кампаний из raw API батча vs
  кэш дала 0 расхождений по spend/revenue/orders. Кэш содержит полный
  набор метрик (spend, orders, revenue, views, clicks) уже в рублях.
  Для сегодняшнего дня кэш неполон — там только live-скрипт.
- Ответы `wb_list_campaigns` / `wb_get_campaign_stats` — сотни КБ JSON
  (вложенные days → apps → nms). Не читать сырыми в контекст: MCP
  сохраняет большие ответы в `/tmp/hermes-results/*.txt` — парсить
  их python-скриптом (поле spend = `sum`, выручка = `sum_price`).
  Ответы >1 МБ (status=7 — 850+ кампаний) могут вообще не сохраниться
  («could not be saved to sandbox») — для массового анализа вызывай
  инструменты из локального скрипта через `WBMCPClient`
  (`/root/.hermes/scripts/wb_mcp_client.py`), а не через MCP-тулзы.
- **Правильный паттерн вызова WB MCP из Python-скриптов (03.08.2026):**
  импортируй `call_with_retry` и `mapping` из `/root/.hermes/scripts/wb_common.py`.
  `call_with_retry(client, tool_name, payload_dict, attempts=N)` — заворачивает
  аргументы в `{"payload": {...}}` автоматически и делает ретраи для
  `rate_limited` (65с), `service_unavailable` (15с), `transport_error` (5с).
  НЕ передавай `payload` на верхнем уровне и НЕ пиши свой retry-цикл —
  `call_with_retry` уже это делает. `mapping(v)` возвращает `v` если dict,
  иначе `{}` — защита от None в полях ответа.
- `wb_get_campaign_stats`: окно date_from..date_to максимум ~31 день —
  60 и 120 дней отклоняются (`request_rejected`, НЕ retryable). Для
  длинных периодов делай несколько окон ≤31 дня и мержи результаты.
- Один невалидный ID в `campaign_ids` валит ВЕСЬ батч (`request_rejected`):
  невалидны реально удалённые кампании (`timestamps.deleted` ≠
  `2100-01-01`) и кампании без `nm_settings`. Перед сбором фильтруй
  список: deleted startswith «2100» И nm_settings непуст.
- `wb_get_campaign_budget` переносит быстрые последовательные вызовы
  (~0.3с между ними, 100+ подряд) — отдельный, мягкий rate limit.

## Диагностика РК: корзина есть, заказов нет (03.08.2026)

Когда `wb_get_campaign_stats` показывает клики и добавления в корзину
(ATB), но 0 заказов — проблема НЕ в трафике/рекламе, а на этапе
**корзина→заказ**. Алгоритм диагностики:

1. Сверь `atbs` (addToBasket) с `orders`: если ATB > 0 а orders = 0 —
   конверсия в корзину работает, ломается дальше.
2. Рассчитай конверсию click→cart: `ATB / clicks * 100` (норма 8–15%).
   Если этот показатель нормальный — реклама нагоняет правильный трафик.
3. Причины 0 заказов при живой корзине: цена выше конкурентов, высокий
   срок/стоимость доставки, FBO=0 (товар только на FBS → долгая доставка),
   0 отзывов (нет социального доказательства), плохие фото/инфографика.
4. Проверь ассоциированные товары в `wb_get_campaign_stats` (вложенный
   `days → apps → nms`) — иногда заказ приходит на другой nmID из той же
   РК, а не на целевой. Атрибуция может быть органической.
5. РК с 0 заказов и ∞ ДРР не означает «плохая РК» — если click→cart
   нормальный, чинить надо карточку (цена/FBO/отзывы), а не отключать РК.

## Раздельная выгрузка остатков FBO/FBS (проверено 30.07.2026)

Когда ЛК не отдаёт остатки — API отдаёт за ~2 минуты:

- `wb_get_stock_products` принимает `stock_type`: `"wb"` = FBO (склады WB),
  `"mp"` = FBS (склад продавца), `""` = всё вместе. Два прогона → раздельный
  срез per nmID. Это основной путь для «выгрузи остатки FBO/FBS отдельно».
- Прямой вызов `wb_get_wb_warehouse_stocks` через MCP-тулзу на полном
  каталоге падает по таймауту (300с); `wb_list_warehouses` с пустым payload
  отклоняется (`request_rejected`). Через `stock_products` оба не нужны.
- ВАЖНО: `stockCount` в отчёте — ТЕКУЩИЙ срез; `date_from/date_to` влияют на
  заказы/оборачиваемость, НЕ на дату остатка. «Остатки на дату X» возможны
  только когда X = сегодня. Задним числом — нет; для истории нужен
  ежедневный срез кроном в локальный файл.
- После инцидентов складов остатки сгоревших висят в FBO до списания WB —
  тотал FBO завышен на «мёртвые» остатки (см. раздел про инциденты).
- Готовый скрипт: `/root/.hermes/scripts/wb_stocks_export_3007.py`
  (WBMCPClient timeout=280, пагинация 1000, агрегация per nmID → xlsx+json
  в `/root/.hermes/data/`). Доставка xlsx Максиму — ТОЛЬКО sendDocument,
  MEDIA документы не носит.

## Расход за вчера, когда stats пустой (проверено 31.07.2026)

- `wb_get_campaign_stats` может отдавать НУЛИ (views=0, sum=0) за вчерашний
  день — лаг финализации статистики WB. Заказы/выручка при этом присутствуют
  (доатрибуция с прошлых кликов). Вывод «кампании не крутились» делать
  ТОЛЬКО после сверки с биллингом.
- Источник истины: `wb_get_campaign_spend_history` (payload: только
  `date_from`/`date_to`, до 31 дня) — реальные биллинг-списания;
  агрегировать `updSum` по датам (`updTime[:10]`). Проверено: stats=0 ₽,
  биллинг=267 340 ₽ за тот же день. Ответ большой (~180 КБ на 4 дня) —
  парсить сохранённый файл, не читать сырым.
- `wb_describe_operation` вызывается с аргументом `tool_name`
  (НЕ `payload.operation`) — через него смотреть обязательные ключи любого
  wb_* инструмента перед первым вызовом.
- Все wb_* MCP-инструменты принимают ЕДИНСТВЕННЫЙ аргумент `payload` с
  объектом внутри: `{"payload": {"campaign_id": 123}}`. Передача параметров
  на верхнем уровне (`{"campaign_id": 123}`) падает с
  «missing required argument(s): payload» (проверено 31.07.2026 на
  wb_plan_update_campaign и wb_get_campaign).
- Ночной pause/resume цикл (кроны 091a96d886cf/0407196e6c89) управляет
  только кампаниями со spend>500 ₽ за день (~3 шт) — «весь аккаунт на
  паузе» он не ставит; нулевой расход по всем РК его виной не является.

## Трекер товаров: полный каталог → Google Sheet (31.07.2026)

- Система ежедневной динамики по ВСЕМ карточкам (~940): скрипт
  `/root/.hermes/scripts/wb_product_tracker.py` (крон no_agent
  `9f24b20c9aca`, 07:30) собирает `wb_get_sales_funnel` за вчера батчами
  по 20 nmID и дописывает строки в Google-таблицу «WB · Динамика товаров
  и изменения» (id в `/root/.hermes/data/wb_product_tracker_sheet.json`).
  Лист «Динамика» = метрики + колонка «Событие дня» (автоподтяжка из
  листа «Изменения»). Запись события правки (SEO/цена/контент/реклама):
  `wb_tracker_log_change.py --nmid N --type SEO --what "..."`.
- ЖЁСТКОЕ ПРАВИЛО Максима (31.07.2026): внешние артефакты (эта таблица
  идёт Елене/коллегам) НЕ должны содержать отсылок к ИИ-инструментам.
  В «Изменения» источник = «менеджер» (дефолт в log_change), никаких
  «Codex», «$wb-seo», «read-back зелёный», «агент» и т.п. Комментарии —
  нейтральные («применено на WB»). Касается любых таблиц/документов,
  уходящих наружу, не только трекера.
- `wb_get_sales_funnel` НЕ содержит CTR/показов — воронка начинается с
  `openCount` (переходы в карточку). Зато отдаёт `vendorCode`, `title`,
  `brandName`, `conversions` (addToCartPercent / cartToOrderPercent /
  buyoutPercent — использовать их, а не самописные CR) и блоки
  `past`+`comparison` (динамика к прошлому периоду). Батч `nm_ids` до ~20
  работает; при ошибке батча — fallback по одному.
- **Структура ответа funnel (проверено 03.08.2026):** данные вложены в
  `data.products[].statistic.selected` (НЕ плоско в корне product).
  Путь: `product → statistic → selected → {openCount, cartCount,
  orderCount, orderSum, buyoutCount, ...}`; динамика —
  `selected.comparison.{openCountDynamic, orderCountDynamic, ...}`;
  прошлый период — `statistic.past`. Два скрипта упали с нулями, пока
  не нашли вложенность. Прямой вызов через MCP-тулзу
  (`mcp__wb__wb_get_sales_funnel`, payload с nm_ids до 1000) отдаёт
  ВСЕ карточки одним батчем — быстрее чем скриптовые батчи по 20;
  использовать его когда возможен ответ <1 МБ.
- Динамика — **просто лента**: каждый день append новых строк, не
  пересортировывать и не группировать вручную. Срезы по артикулу/дате
  делаются на отдельных листах/графиках.
- При старте трекера полезно накопить базу «до/после» вокруг даты
  изменения: для карточек с событиями (SEO/цена/контент/реклама) сделать
  бэкфилл на 2–3 дня до события. Автоподтяжка «Событие дня» работает
  через лист «Изменения»: строка с `nmID`, датой и текстом события
  автоматически попадает в колонку `Q` листа «Динамика».
- Лист **«График»** (отдельный пример реализации в локальном комплекте отсутствует; ниже сохранено описание, а не проверенный рецепт восстановления):
  выпадайка артикула продавца в `B1`, QUERY на хелпер-зоне, комбо-чарт
  по всем метрикам кроме остатков и рейтинга, вехи-дни изменений звёздами
  на линии заказов. См. раздел «Грабли Google Sheets» ниже.
- Лист **«Изменённые»** (31.07.2026, по запросу Максима): живой вид
  «динамика только по артикулам с правками». Одна формула в A2:
  `=SORT(FILTER('Динамика'!A2:Q; COUNTIF('Изменения'!B$2:B$1000; 'Динамика'!B2:B)>0); 3; TRUE; 1; TRUE)`
  (сорт: артикул → дата). Новый nmID в «Изменения» → его строки
  подтягиваются автоматом, ничего пересобирать не надо.
- Дропдаун `График!B1` ограничен ИЗМЕНЁННЫМИ артикулами (решение Максима
  31.07): `_lists!C1` = `=SORT(UNIQUE(FILTER('Изменения'!C2:C;'Изменения'!C2:C<>"")))`,
  валидация B1 переключена на `ONE_OF_RANGE('_lists'!$C$1:$C)` через
  `sheets_set_validation`. Полный список всех артикулов остаётся в
  `_lists!A:A` — вернуть «выбор из всех» = одна правка валидации.
- Бэкфилл истории: `/root/.hermes/scripts/wb_tracker_backfill.py

## Грабли Google Sheets при работе с трекером (31.07.2026)

- **OAuth-токен и scope**: после ручного OAuth не передавать `scopes`
  в `Credentials.from_authorized_user_file()` — если токен протухает,
  refresh с узким набором scope выдаёт `invalid_scope`. Загружать так:
  `Credentials.from_authorized_user_file('/root/.hermes/google_token.json')`.
- **Локаль `ru_RU`**: формулы, внесённые через API, используют `;`
  как разделитель аргументов (не `,`). `QUERY`, `ARRAYFORMULA`, `FILTER`
  и прочие ломаются с `#ERROR!` при запятой.
- **COMBO-чарт не принимает SCATTER-серии**: для вех используй линию с
  `"lineStyle": {"width": 0}` + крупный `"pointStyle"` (звезда). Чтобы
  легенда серий подтягивалась, диапазон серии должен включать заголовок
  (`startRowIndex` = строка заголовка) и `headerCount: 1`.
- **Не оставлять ИИ-отсылок** во внешних артефактах: в «Изменениях»
  источник = «менеджер», никаких «Codex», «$wb-seo», «read-back»,
  «агент». Это правило Максима для любых таблиц/документов, уходящих
  коллегам.

## Seller analytics umbrella

Use this skill as the class-level entry point for WB seller data, advertising, stock, SEO, and controlled campaign changes. Select the topical lane below; use only explicit `wb` tools and current schemas.

### Analytics and freshness

- Label every result with source, date, and freshness; separate live calls from SQLite cache because stale cache or cron status does not prove current absence.
- Treat missing rows as unknown until completeness is established, and aggregate sales, returns, spend, and revenue with explicit date boundaries.
- Respect sequential stats batches and rate limits; keep large raw responses in files and compute totals programmatically.

### Advertising and campaign writes

- Keep read-only analysis separate from write proposals; show the exact allowlist, amount, source, and total before confirmation.
- Use plan → explicit confirmation → one apply → independent read-back for every manual write, and stop further mutations on an unknown outcome.
- Before creating campaigns, search active/paused duplicates and preserve a proposal; never create or launch automatically.
- For pause/resume automation, require current cron ownership, durable lock/journal/control state, fresh fingerprints, unique receipts, and fail-closed recovery.
- Low-stock alerts use live same-day spend and both active and paused campaign statuses; weekly cache spend is not a substitute.

### Card SEO and content

- Separate SEO audit/proposal from Content API writes; preserve the full card, validate limits and semantics, and present a reversible diff before applying.
- Keep SEO and advertising scopes separate, and do not route WB SEO through an unrequested coding delegate.


Перед подготовкой или выполнением любого write-flow сначала загрузи этот scoped skill через `skill_view(name='wb-seller-analytics')` и дочитай соответствующий профильный write reference. Аналитический read-only вызов не заменяет эту проверку. Любая запись дальше идёт только через подтверждаемый plan/apply flow с read-back; без явной проверки scope — fail closed.

## Работа с поисковыми кластерами РК

Для выгрузки и аудита фраз загружай `wb-search-query-audit`. Добавлен read-only MCP `wb_get_search_cluster_stats` → `POST /adv/v1/normquery/stats`: дневные показы, клики, расход, корзины и заказы по кластерам (до 100 пар campaign_id/nm_id). Не путать со списком `wb_get_search_clusters` без метрик. Если каталог текущего соединения старый — новый WBMCPClient вызывает метод напрямую через MCP; ручная выгрузка из кабинета больше не обязательна.

Перед любым управлением кластерами сначала получай полный текущий список active/excluded через `wb_get_search_clusters` и сохраняй read-back. **Кластер допускается к рассмотрению только если WB показывает по нему не менее 100 просмотров/показов.** Кластеры с метрикой ниже 100 не анализируй для управления и не включай в payload минус-фраз: WB может не принять работу с ними. Если метрика просмотров/показов для конкретного кластера недоступна в доступном источнике, статус `needs_check`, не подменяй её просмотрами карточки из `wb_get_search_queries` или показами всей РК из `wb_get_campaign_stats`.

Рабочий порог применяется до семантической оценки: сначала `views/impressions >= 100`, затем проверка релевантности по карточке, характеристикам и изображениям. При изменении минус-фраз передавай полный актуальный список, а не только новые элементы: частичный payload может удалить остальные значения. После подготовки показывай diff `было → станет`; запись выполняй только после явного подтверждения и через подтверждаемый plan/apply flow.

1. перечитать живой объект;
2. показать пользователю цель, значения и последствия;
3. получить явное подтверждение;
4. создать `wb_plan_*`;
5. применить ровно один раз через `wb_apply_change`;
6. проверить результат новым read-вызовом.

Пополнение бюджета — один запрос без автоматического ретрая. Создание,
пополнение и запуск кампании — три отдельные операции.
